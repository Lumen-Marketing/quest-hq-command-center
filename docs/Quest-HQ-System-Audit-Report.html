1 · Executive summary

In plain terms: the foundations of Quest HQ are strong, but a handful of issues can quietly corrupt data or confuse users, and the app is doing far more work behind the scenes than it needs to.

We reviewed the entire Quest HQ system across six independent tracks — client (browser) security, back-end & database security, software architecture, correctness/bugs, performance, and user experience/accessibility. Every issue in this report was confirmed by reading the actual code, not guessed.

The good news. The parts that protect customer data are well built. The back-end and database enforce strict tenant isolation, block cross-company access, verify payment webhooks, and harden their database functions. Our security review found no critical break-ins — no way for one company to read another's data, no injection holes, no leaked secrets in the code.
Where to focus. The risk lives in three areas: (1) the in-progress "contact filter rail" ships buttons that look clickable but do nothing; (2) several paths can silently corrupt or lose data (a spreadsheet import that puts phone numbers in the email field; a text message that can vanish without warning); and (3) the app rebuilds its entire screen on every tiny change, which wastes performance and interrupts users mid-typing.

4 · Priority 0 — Ship-blockers 5

These should be resolved before the current contact-rail work is released. They are active breakage, data corruption, or a security hole.

P0-1“Team / Private” tabs do nothingUX · in-progress work
What it meansThe new contact panel shows a “Team / Private” switch that looks fully functional but is not connected to anything. Clicking it gives no response, which reads as a broken app.
Technical detailThe buttons are rendered with active/inactive styling but carry no data-action and have no handler anywhere. src/main.js:8400
FixWire to a real state key with a handler and filtered data, or remove the tabs until the feature exists.
P0-2“Show more” is dead — some filters are unreachableUX · in-progress work
What it meansEach filter group only shows the first 7 values; the rest hide behind a “Show more” link that doesn't work. Because this panel is now the only way to filter, any 8th-or-later value (e.g. the 8th owner) can't be selected at all.
Technical detailvalues.slice(0,7) caps the list; “Show more” is a plain <span> with no action. src/main.js:8379, 8393
FixMake it an expanding button (track expanded groups in state) or paginate.
P0-3No way to see or clear active filtersUX · in-progress work
What it meansThe old “active filters” bar (with per-filter remove chips and a “Clear all”) was removed. Users can end up with a narrowed list and no clear indication of why, and the only reset clears everything at once.
Technical detailrenderContactFilterBar is still defined but never called; its remove-contact-filter handler is now dead code. src/main.js:8410 (unused)
FixRestore a compact active-filter chip strip in the toolbar (reuse activeContactFilters()); delete the orphaned handlers.
P0-4Contact import puts data in the wrong fieldsCorrectness · data corruption
What it meansWhen importing a contacts spreadsheet, any blank cell shifts every following column one place to the left — so a phone number can land in the email field and be lost, silently.
Technical detailThe row splitter /(?:"[^"]*"|[^,])+/g skips empty fields. Example: header Name,Email,Phone with row John Doe,,555-1234 → email becomes the phone number. src/main.js:8320
FixRoute imports through the existing correct CSV parser wbParseCsv (src/main.js:14365). One change also fixes P2 items on multi-line fields and decimals.
P0-5Malicious “app file” can run code for teammatesSecurity · stored XSS (High)
What it meansThe Workspace App Builder lets a user install an app from a .questapp.json file. A crafted file can smuggle in a hidden script that then runs in every teammate's browser when they view the workspace — potentially stealing their session.
Technical detailImported color values are copied verbatim (no format check) and interpolated into style="…" without escaping in ~6 places, allowing attribute break-out. import src/main.js:14523; sinks 13536, 14031, 14278
FixValidate every color against ^#[0-9a-fA-F]{3,8}$ at the import boundary; escape at the sinks. Enforcing CSP (P2-18) adds a second layer.

5 · Priority 1 — High severity 7

Real bugs and risks users or customers will encounter. Schedule for the next work cycle.

P1-6The app rebuilds the entire screen on every changePerformance · systemic
What it meansEvery small update — a click, a background sync, a 15-second phone-status poll — throws away and rebuilds the whole page. This wastes performance, and it can interrupt users mid-typing and reset their scroll position. It is the single biggest lever in this report because it also causes several other problems.
Technical detailrender() reassigns app.innerHTML for the entire shell + page + command palette, invoked from ~549 sites, plus a 15s poll, a 5s portal poll, and ~45 realtime table subscriptions. Also reboots the embedded Tasks iframe on background refresh. src/main.js:2717
FixCoalesce renders through a single animation-frame scheduler, and update only the changed region rather than the whole page. Highest ROI change in the codebase.
P1-7“Today” is off by one day in the eveningCorrectness · timezone
What it meansFor the US/Arizona team, after about 5pm the app starts treating tomorrow as “today.” The dashboard's “today's dispatch,” the mini-calendar highlight, and automation due-dates all drift by a day.
Technical detailisoDate() returns a UTC date while surrounding logic uses the local date. src/main.js:38588
FixCompute the local date in isoDate(), or standardize all “today” comparisons on one basis.
P1-8Incoming text messages can vanish silentlyCorrectness · data loss (API)
What it meansIf two texts arrive from a brand-new number at nearly the same moment, one message can be dropped with no error and no retry — the customer's reply simply disappears.
Technical detailOn a contact-insert race the code falls back to a non-existent contact id, the message insert fails its foreign key unchecked, and the webhook still returns {ok:true} so the provider never retries. api/sms-inbound.js:46
FixRe-select the existing contact on insert failure; check the message insert result and return a non-2xx so the provider retries.
P1-9Saving portal notes can wipe existing onesCorrectness · data loss (API)
What it meansWhen a client saves annotations in the portal, the system deletes all their existing notes first, then re-adds them. If the re-add fails midway, every note is gone with no recovery.
Technical detailDelete-then-reinsert with no transaction. api/client-portal-annotations.js:71
FixPerform the replace inside a single database transaction/RPC, or insert-then-delete-stale.
P1-10Abuse protection is weaker than it appearsSecurity · anti-automation
What it meansThe rate limit that's supposed to stop attackers from guessing secret links or portal passwords resets often and can be sidestepped, so guessing attacks are more feasible than intended.
Technical detailThe limiter is in-memory per serverless instance (effective limit = limit × warm instances, resets on cold start) and keys off the spoofable leftmost X-Forwarded-For. It is the sole control behind proposal/invite token enumeration and portal-password guessing. api/_lib/rate-limit.js:3; http-security.js:24
FixBack the limiter with a shared store (e.g. Vercel KV / Redis / a Postgres table); use the platform-provided client IP.
P1-11Keyboard users can't select or edit contactsAccessibility
What it meansSomeone using only a keyboard (including many screen-reader users) cannot tick a contact's checkbox, use inline edit, or reach the row menu. This is an accessibility and compliance gap.
Technical detailRow checkboxes are tabindex="-1" inside a plain <span data-action>; inline-edit fields are non-focusable spans; the row-menu dots and header chevron are dead affordances. src/main.js:8112, 8515
FixUse real <button> elements (or add role + tabindex + key handlers); make the checkbox itself focusable.
P1-12Recurring tasks can reappear already overdueCorrectness · scheduling
What it meansIf a repeating task is completed late, the next copy is created with a due date in the past. The user then has to clear weeks of “historical” tasks to catch up.
Technical detailThe next occurrence anchors to the old due date and advances exactly one interval, with no roll-forward past today. src/main.js:9009
FixAfter computing the next date, advance whole intervals until it is on or after today.

7 · Priority 3 — Architecture (OOAD) long-term

These are maintainability risks, not bugs. They make future changes slower and more error-prone. The recommended approach is incremental — no risky “big rewrite.”

In plain terms. Almost the entire application lives in one enormous file. It works, but it means every change carries a risk of accidentally breaking something unrelated, and it's hard to test in isolation. Tidying it up gradually will reduce bugs and let the team move faster.

Measured facts

One file, many jobs
main.js = 38,781 lines holding routing, screens, data access, business rules, and events together (~2,073 top-level symbols).
Shared mutable state
228 fields in one global object, referenced 2,435× — any function can change anything.
Giant dispatchers
handleAction = 2,055 lines / ~309 branches; a second is 529 lines. Adding a feature means appending to these.
Database calls in the UI
252 table calls + 42 stored-procedure calls inline in the screen code — no data-access layer.
Tests
52 of 96 test files check that certain text exists in the code, not that it works — they pass even if the feature is broken.
Plugin system
Adding a plugin requires editing the monolith and a hand-copied database rule — the source of a known drift bug.
Recommended single highest-leverage move. Introduce a per-feature “registry” so each feature owns its own actions, screen, and data in a small module instead of adding to the giant shared functions. This can be done gradually, one feature at a time, and it simultaneously (a) creates safe boundaries, (b) makes the plugin system properly extensible, and (c) finally makes real (behavioral) testing possible. It is fully compatible with the team's existing decision to avoid a big-bang split.

8 · What's already done well

An audit should be balanced. These are verified strengths worth protecting as the code evolves.

  • Tenant isolation is enforced twice — database row-level security for logged-in users, plus explicit company scoping on server paths. No way found for one company to read another's data.
  • Database functions are uniformly hardened — all 111 privileged functions across 37 migrations set a fixed search path; sensitive ones revoke public access and re-check permissions server-side.
  • Payment & messaging webhooks are properly verified — Stripe signatures and cron secrets use correct, constant-time checks.
  • A recorded past privilege-escalation hole was correctly closed, and invites fail safe (any elevated role request is downgraded to “member”).
  • Output is consistently escaped in the browser via a correct helper, and heavy libraries (maps, PDF, zip) are loaded only when needed.
  • No secrets are committed to the repository.
  • The code documents its own reasoning inline and maintains a vendor-neutral “project brain,” which made this audit faster and safer.
